# Spotify: feasibility (researched 2026-10-10) and what is built

The question: could TurboMusic (1) play tracks that are not on the server through Spotify, (2) control Spotify, and (3) use Spotify for recommendations? Short answer: **(2) and a limited (1) are feasible for one Premium user; (3) is not, with Spotify's own API.** Sources were web searches; Spotify's developer site itself could not be fetched from the sandbox, so each point below is marked with how well it is confirmed. Re-read the linked pages before building anything.

## What is available

| Option | What it gives | Fit |
|---|---|---|
| **Spotify Soloist** ([announcement](https://developer.spotify.com/blog/2026-08-13-introducing-spotify-soloist), [docs](https://developer.spotify.com/documentation/soloist), [GitHub](https://github.com/spotify/soloist)) | An official headless Spotify Connect client for Linux/Raspberry Pi. It shows up as a normal device in the Spotify apps. Optional local **WebSocket API** (`--ws ADDR:PORT`): JSON text frames with `"type": "command"` (play, pause, seek, volume, shuffle, repeat, add to queue, `get_queue`), plus playback events. | **Best fit.** The Pi that already runs the TurboMusic server can run it, and the server can bridge it to every client. |
| **Web API** ([Feb 2026 migration guide](https://developer.spotify.com/documentation/web-api/tutorials/february-2026-migration-guide)) | Search, library, playlists, and "transfer playback / play this URI on that device" for a Premium account. | Works for control and for finding a Spotify match of a TurboMusic track. Heavily restricted (below). |
| **Web Playback SDK** | Turns a browser tab into a Spotify Connect device (Premium only). | Works only in a browser; not in the Android WebView app (needs Widevine/EME and Spotify does not support WebViews) and not for Android Auto. Not verified here: the SDK pages did not come up in search. |
| **Android App Remote SDK** | Controls the installed Spotify app from your app. | Remote control only: the Spotify app plays, TurboMusic cannot get the audio or put it through its own queue/EQ. |

## Constraints that decide it

- **Premium is required** for the Web API in Development Mode, the app owner's Premium must stay active, and Development Mode is limited to **5 users and 1 client ID** per developer (official migration guide; applies to new apps from 2026-02-11 and to existing ones from 2026-03-09). That is fine for a personal app, not for sharing it.
- **Extended access** (more users) is reserved for established organisations; third-party sources say about 250k monthly users. Not an option here.
- **Recommendations are not coming back.** The *Get Recommendations*, *Audio Features*, *Audio Analysis* and *Related Artists* endpoints were closed to apps that did not already have extended access on 2024-11-27 (reported by several third-party write-ups; Spotify's changelog excerpts retrievable here did not list them, so treat as likely, not certain). A new personal app should assume it has none of them.
- **Soloist** needs an API key generated at Spotify for Developers by a Premium account (keys are personal and must not be shared or put in client-side code, and are needed at every start). Its WebSocket API has **no authentication or TLS**, so it must stay on localhost or the home network; the TurboMusic server would proxy it with its own token. The queue it reports is capped (a third-party blog says 80 tracks; unconfirmed).
- Spotify content cannot be downloaded, cached, equalised by us or mixed into TurboMusic's own queue as audio: Spotify plays it, TurboMusic only sends commands. So the equaliser, the app's own player and offline mode do not apply to Spotify tracks.

## What could be built, in order of value

1. **Play on Spotify when a track has no file.** A track has `spotifyUrl` (443 of 444 in the migrated library do). With Soloist (or any Connect device) TurboMusic can send "play this URI". Needs: server module `spotify.ts` holding the OAuth refresh token (Authorization Code with PKCE; Web API `PUT /me/player/play` with the Soloist device id) or a direct Soloist WebSocket connection; a "Spotify" source in the player that is remote-controlled like the existing Connect devices (the Connect hub already has the shape: a device with state, commands, hand-over). Queue rules ("play B right after A") could be honoured by sending the next URI when the first ends.
2. **Show and control Spotify from TurboMusic** (now playing, pause/skip, volume): free once (1) exists, via Soloist events.
3. **Recommendations without Spotify's endpoint:** build them from TurboMusic's own data (votes and ratings already give a taste profile) plus another source: MusicBrainz/ListenBrainz (open, has similar-artist and recommendation APIs) or Last.fm `artist.getSimilar`. Spotify would only be used to *play* what these suggest, via Search. This is the realistic route and does not depend on Spotify's policy.

## Risks and open questions

- Spotify has repeatedly narrowed its API (2024-11, 2025-04, 2026-02). Anything depending on Development Mode can change under us.
- Soloist is new (announced 2026-08-13); its stability on a Pi, gapless behaviour and the 80-track queue figure are unverified. Nobody has run it here.
- Terms of use for apps that mix Spotify playback with non-Spotify sources: not found in search, read the Developer Terms before shipping anything public. For private use it is a personal app on a personal key.
- Android Auto/notification controls would show Spotify's own session, not TurboMusic's, when Spotify is the source.

## Suggested next step

Run Soloist on the Pi with `--ws 127.0.0.1:PORT`, and try one `play` command by hand from `soloist ctl` or a WebSocket client. If that works, a first version (play a Spotify URI for a file-less track, show state) is a small server module plus one more device kind in the Connect list.


## Update 2026-10-11: what is built (import side only), and what the research changed

**Built, all modular in `packages/server/src/spotify.ts` and `match.ts`, tested against fake Spotify/YouTube servers; none of it has run against the real services (the sandbox cannot reach them):**

| Piece | What it does | Needs |
|---|---|---|
| oEmbed (`open.spotify.com/oembed`) | title + cover of a track/album link, no key | nothing |
| Public embed page (`/embed/playlist/<id>`) | the track list of any **public** playlist (title, artists, duration; **no album names**) | nothing; unofficial, can break |
| Own sign-in (Authorization Code + **PKCE**, no secret) | full details (albums, durations) of **your own** playlists | a Spotify developer app (Premium owner), its client id |
| Account data file (`Playlist1.json`, `YourLibrary.json`) | every playlist and your liked songs, read in the browser | the "Account data" download from spotify.com/account/privacy |
| Typed list / history | `Artist - Title` lines; album names also come from imported streaming history | nothing |
| yt-dlp playlist search | the YouTube Music album of an album a Spotify import started (Health › Find YouTube Music albums), then imported one release at a time | yt-dlp on the server |

Sign-in works from any machine: the page opens Spotify's authorize URL, and you paste back the address Spotify redirects to (even if that page fails to load); the server also answers `/api/spotify/callback` directly when the redirect URI points at it (`http://127.0.0.1:47813/api/spotify/callback` by default, which Spotify allows over http for loopback only).

**Research that changed the plan (Feb 2026 Development Mode changes; confirmed by several third-party reports, the official guide page itself could not be fetched):**
- In Development Mode, **playlist contents are only returned for playlists you own or collaborate on** (so "any public playlist" cannot go through the API; it uses the embed page instead, and "my playlists" uses sign-in).
- The playlist list endpoint is now `/items` (was `/tracks`); the code tries `/items`, then `/tracks`.
- Several browse endpoints, track-by-id lookups and "many albums at once" were removed or reduced; search results are capped (reported as 10). So the album tracklist cannot be trusted to come from Spotify: **the album is completed from YouTube Music instead** (Library health > "Albums waiting for a YouTube album link").
- Reports say the owner of a Development Mode app must keep Premium, max 5 users, 1 client id per developer.

**Not built, needs a decision (see the open questions in CLAUDE.md):** playing tracks that are not on the server through Spotify, controlling Spotify, and recommendations. Spotify's recommendation endpoints stay closed to new apps, so recommendations would come from your own votes plus ListenBrainz/Last.fm.


## Decision 2026-10-11: the mix (Soloist + Web API), built
The user chose to combine the two best routes, has Premium, and wants recommendations from votes + ListenBrainz.
- **Playback/control = the Web API, with Soloist as one of the devices it controls.** Soloist (headless Connect client on the Pi) shows up in `GET /me/player/devices` like any speaker, so TurboMusic needs only the documented player endpoints (`PUT /me/player/play`, `pause`, `seek`, `volume`, `POST next/previous/queue`, `PUT /me/player` to transfer). No Soloist-specific WebSocket protocol is used, because its message format could not be verified. A phone or PC running Spotify works the same way. Sign-in needs the playback scopes (`user-read-playback-state user-modify-playback-state user-read-currently-playing`): sign in again after updating.
- **How it plays** (`apps/web/src/lib/spotifyPlayer.ts`): a track with no audio file but a Spotify link is sent to the Spotify device chosen in Settings > Spotify (`spotifyDeviceId`, per device). It is a third engine next to the page's `<audio>` and the Android player: TurboMusic's own queue and playback rules decide what is next (one track is sent at a time; the end is detected by polling the player state every 2.5 s, position interpolated in between). Verified in Chromium against a fake Spotify server: play, pause, resume, end of track starts the next queued one. Not verified: real Spotify, Soloist, gaps between tracks (there will be a short one), Android (the app's notification shows its own session, not Spotify's).
- **Recommendations** (`/discover`): seeds = artists whose tracks you rate 6+ with 3+ comparisons (`lib/recommend.ts`), similar artists from MusicBrainz (name -> id) + ListenBrainz labs (`server/src/recommend.ts`, endpoint and response shape from memory, UNVERIFIED), merged and filtered against your library; "Hear" finds tracks with Spotify search (Development Mode returns few), play them on the device, or Add them as singles (then find their YouTube link in Health).

## Update 2026-10-11 (later): Spotify devices in the cast list, Soloist as a module, several links per song
- **Devices.** The cast button in the player bar lists your TurboMusic devices and, under **Spotify devices**, every device Spotify reports for your account (Soloist, the phone's Spotify app, a speaker). Click one to make it the place Spotify tracks play on this device (a per-device setting, `spotifyDeviceId`); if a Spotify track is playing, it moves there with the playback (`PUT /me/player`). The player bar says **Playing on <device>** while a track plays through Spotify (`engine: 'spotify'` in `lib/player.ts`). The device radio list in Settings is gone.
- **Soloist module** (Settings → Server → Spotify → "Soloist: play Spotify inside TurboMusic"; `packages/server/src/soloist.ts`). Three steps: *Install* downloads Spotify's own build from `https://soloist-builds.spotifycdn.com/soloist_release_<arm64|arm32|x86_64>.tar.gz` onto the server (TurboMusic does not ship it: Spotify asks that nobody redistributes the archives), *API key and name* are saved in `<data>/soloist/config.json` with mode 0600 (the key is never sent back to a page), *Run* starts `soloist --device-name <name> --api-key <key> --cache-dir <data>/soloist/cache` and keeps it alive (a crash restarts it, up to five times). The device then appears in the cast list and is chosen automatically if nothing was chosen. Builds stop working 90 days after they were built and exit with code 10: the server notices, downloads the current build and starts it again. It needs a Premium account to make the key (Spotify for Developers → Soloist), PipeWire or PulseAudio on the machine, and Linux on arm64, armv7 or x86_64. Everything is from Spotify's documentation as found in search results (flag names `--device-name`, `--api-key`, `--cache-dir`, `--ws`; the archive names; the 90-day rule and exit code 10); **nothing has been run against Spotify's download server or a real Soloist from the build sandbox**, so the first install is the real test: its own log is shown under "Soloist's own messages".
- **Several Spotify links per song.** A single that later comes out on an album is two Spotify tracks of one song. The track editor now has *Spotify URLs*: the first is played, the others are alternates (`TrackData.spotifyUrls`). Listening-history matching, Spotify import and the duplicate merge all know every link, so a play of either version counts for the one track, and importing the album version of a song you already have adds its link instead of a duplicate.
- **Merging duplicates** (Health → Possible duplicate tracks → *Merge these*). Pick the track to keep (the one with the most votes, then audio, then an album): it takes every Spotify link, the YouTube/Genius links, memories (summed), a cover and audio it lacked, genres and album links, and everything that pointed at the others (releases, album order, playlists and their notes, eras, votes, plays, notes, "play B after A" rules) points at it. A vote between the two duplicates is dropped. "Feat." credits in titles are ignored when looking for duplicates; "(Remix)" is not.
- **Discover** fixes: the ListenBrainz algorithm string is now the one verified live in October 2026 (`session_based_days_7500_session_300_contribution_5_threshold_10_limit_100_filter_True_skip_30`, falling back to the old one), seeds are no longer limited to artists averaging 6+ (the best of the rest fill up to five), and the page lists the seed artists the open data had nothing for.

## Update 2026-10-11 (latest): Spotify inside the app (Web Playback SDK)
Settings > Spotify > **Play Spotify inside this app**. Spotify's own Web Playback SDK (`https://sdk.scdn.co/spotify-player.js`) runs in the page and turns this browser into a Spotify Connect device named "<this device> (TurboMusic)"; TurboMusic's existing Spotify engine then sends it tracks through the server's account, so the queue and playback rules work as for any other Spotify device. Spotify decodes and plays the audio: no equaliser, no offline copies.
- **Needs**: Premium; a secure page (https or `localhost`: plain `http://<pi>:47813` on the LAN is not, use Tailscale/https); a browser with Widevine (Chrome, Edge, Firefox, Safari; Spotify's web-player help also lists Android Chrome and Samsung Internet). The check is `navigator.requestMediaKeySystemAccess('com.widevine.alpha')`; when it fails the setting says so and nothing is started.
- **Not possible in stock Electron** (no Widevine; Spotify's developer forums say the SDK is not meant for Electron). On a Linux desktop use Soloist (it runs inside the desktop app), elsewhere pick the Spotify app on that computer in the cast list. **Not in the Android app**: its WebView has no Widevine (confirmed by the user), so the option is hidden there and the SDK is never started. On Android, Spotify tracks play through Soloist on the server (it plays through the server's speakers) or through the Spotify app on the phone, chosen in the device list.
- **Sign in again once**: the sign-in now asks for `streaming user-read-email user-read-private`. An older sign-in lacks `streaming`; the setting tells you to sign out and in again. The server hands the page a short-lived access token at `GET /api/spotify/sdk-token` (the refresh token stays on the server).
- Verified in Chromium against a real TurboMusic server with Spotify's script and API faked (device registers, the file-less track is sent to it, "Playing on …" shows, switching it off disconnects); the "no Widevine" message too. **Not verified against real Spotify**: the sandbox cannot reach it, and headless Chromium has no Widevine.

## Update 2026-10-11 (latest): beaming Soloist's sound to the apps
Soloist can only play on the machine it runs on. **Settings > Spotify > Soloist > "Send the sound to the apps"** changes where that sound goes: Soloist is started pointed at a virtual output (a PulseAudio/PipeWire null sink called `turbomusic_spotify`, created by the server with `pactl`), the server listens to it with ffmpeg (`-f pulse -i turbomusic_spotify.monitor`, MP3 192 kbps) and serves it as a live stream at `GET /api/soloist/stream` (token via `Authorization` or `?token=`; ffmpeg runs only while somebody listens). Any TurboMusic app plays that stream whenever its Spotify device is that Soloist: the **Android app through its own player** (notification, lock screen, keeps playing with the screen off), browsers and the desktop app in an `<audio>` element. The Pi itself stays silent. Pause stops the stream and resume starts it again, so old buffered sound is never replayed. Device setting: "Hear it on this device" (`spotifyBeam`, default on).
- **Needs on the server**: Soloist, a sound server for the service account (`scripts/setup-pi-audio.sh` installs PipeWire, `pulseaudio-utils` and ffmpeg), `pactl` and an ffmpeg with the pulse input (Debian's has it).
- **Limits**: the sound is live, a few seconds (about 3 to 6) behind what the screen shows; one capture is shared by all listeners (everyone hears the same thing); the Android notification says "Spotify, through TurboMusic" (the track's name is shown inside the app, not in the notification); it re-encodes Spotify's audio, which Spotify's terms may not like (checked by the user, not by me).
- **Verified here with a real PulseAudio**: a virtual output, a tone played into it, the real server captured it and served valid stereo 44.1 kHz MP3 over HTTP (tone audible), ffmpeg started and stopped with the listener, and in Chromium the app played the stream and stopped it on pause. **Not verified**: real Soloist, the Android app's player, the notification, how long it stays connected over hours, battery use.

## Update 2026-10-12: Spotify tab, Pi-only Soloist, local volume, "Play on this device only"
- **Settings > Spotify** is its own tab (account, "Check the connection", the in-app player option, Soloist).
- **Soloist runs on the Raspberry Pi only.** The server offers it only on a machine whose device-tree model says "Raspberry Pi" (`TURBOMUSIC_SOLOIST=1` on the server allows another Linux machine); the desktop app's built-in server says "not in this app". The Soloist panel and the cast list name the machine: "Runs on: turbomusic-pi · Raspberry Pi 5 Model B", "Soloist on turbomusic-pi". (This replaces the earlier idea of Soloist inside the Linux desktop app.)
- **Two volumes.** *Soloist's volume* (Settings > Spotify > Soloist) is Spotify's volume for that device, set through the Spotify API, so it takes a moment: set it once (a high level is best). The **player-bar slider** changes the sound on the device you are using at once: while Spotify is beamed (`lib/beam.ts`) it only turns the local stream down and sends nothing to Spotify; without beaming it still sets Spotify's volume.
- **Cast popover**: a "Sound is coming from" line, sections (This device, Other TurboMusic devices, Spotify devices) and, whenever something that is not local is connected (another device controlled, a Spotify device chosen, Spotify playing), **Play on this device only** (`localOnly()` in `lib/connect.ts`): stops controlling other devices, pauses Spotify, stops the stream and forgets the chosen Spotify device so the next local track starts at once.
- Sliders have a 24 px grab area (`.bt-hit`) around a thin bar.
